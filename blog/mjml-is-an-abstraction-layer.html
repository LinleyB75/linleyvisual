MJML Is an Abstraction Layer: Five Faults I Could Only Fix in the HTML and CSS

Published 7 November 2026 • By Linley Bignoux • From the build of: Kick Off → Your English abandoned cart email

mjmlhtmlcssemail-developmentoutlookdark-modegmailvmlfundamentals

The claim

I write most of my emails in MJML, and I am glad of it. It writes the nested tables, the Outlook conditional comments and the responsive columns for me, and its strict mode stops some mistakes. But MJML is an abstraction layer. It sits on top of HTML and CSS, an email client never sees it, and every fault in this post lived underneath it.

In every project I end up in the HTML and CSS, many times: to change a spacing, to fix how one email client draws something, to read what the build produced, or to hand a developer a file with no build step. Vanilla HTML and CSS are the foundation of email development, and knowing them is what lets me use MJML as a tool and not as a crutch.

These five faults come from one build, the abandoned cart email for Kick Off → Your English, which I describe step by step in the full build post. The email in it is a test version. The test I apply to each fault: could I have fixed it without reading the HTML? In every case, no.

Fault 1: a button that was drawn as a paragraph

The draft's button, in MJML, looked fine. It had a fixed width, and no link yet:

<mj-button css-class="button" align="left" background-color="#0055FF"
           font-family="Tahoma, serif" inner-padding="20px 35px" width="380px">
  Return to Your Cart
</mj-button>

This is what MJML built from it, shortened:

<td align="center" class="button"
    style="font-size: 0px; padding: 0; word-break: break-word; width: auto; display: flex; text-align: center;">
  <table style="border-collapse:separate;width:380px;line-height:100%;">
    <tr><td bgcolor="#0055FF" style="border-radius:12px;background:#0055FF;">
      <p style="display:inline-block;width:310px;background:#0055FF;color:#ffffff; ... padding:20px 35px;border-radius:12px;">
        Return to Your Cart
      </p>
    </td></tr>
  </table>
</td>

Three separate facts are in that output, and none is in the MJML:

  • It is a paragraph, not a link. With no href, MJML draws a <p>. It looks like a button and does nothing when pressed.
  • The table is 380px wide, inside a column with 30px of padding on each side: 380 + 60 = 440. The page was 440px wide on a 320px phone, and on a 414px one.
  • My own CSS rule became display: flex on a table cell. A table cell is not a flex container in any useful way, so that line did nothing except make the cell harder to reason about.

Once the button had a link, MJML built an <a> in its place:

<a href="https://example.com/cart" style="display:inline-block;background:#0055FF;color:#ffffff; ... padding:20px 35px;border-radius:12px;" target="_blank">Return to Your Cart</a>

I removed the fixed width and the rule, and the button became 254 × 70px at every screen size. My checks now refuse a button with no link, because strict mode does not: I tested MJML 5.4.1, and it accepts a button with no link without complaint.

Fault 2: a rounded corner on the wrong element

I wrote the whole email a second time by hand, as plain HTML with no MJML, and compared it with the MJML build pixel by pixel, in light and dark mode. My first attempt was identical in light mode and 60 pixels off in dark mode. All 60 were in the corners of one box: the white box holding the heading in the orange band. They differed from MJML's by a single colour level out of 255.

The cause was where the corner lived. MJML puts the rounded corner on the table itself, with the text cell directly inside:

<table style="background-color:#FFFFFF;border-radius:8px;vertical-align:top;border-collapse:separate;" width="100%">
  <tr><td class="dm-text" style="padding:10px 25px;"> ...the heading... </td></tr>
</table>

I had put it on a cell, two tables deeper:

<table width="100%">
  <tr><td style="background-color:#FFF;border-radius:8px;vertical-align:top;">
    <table width="100%"><tr><td class="dm-text" style="padding:10px 25px;"> ...the heading... </td></tr></table>
  </td></tr>
</table>

Moving the corner to the table made the two builds exactly equal. It also showed me something about my own design. This is the top-left corner of that box, enlarged: dark mode on the left, light mode on the right.

In light mode the corner is rounded. In dark mode it is square, because my dark rule also paints the column's square wrapper behind the rounded table, and that covers the corner. Both builds do exactly this, which is why the test passed. It is a small flaw in my dark design, found only because I had to match the two builds, and it is still to fix.

Fault 3: the rounded button in Outlook for Windows

Outlook for Windows draws email with a different engine from a browser, and it does not give a link rounded corners. The usual answer is VML, a shape drawn inside conditional comments. It is not MJML. I write it by hand in a raw block, and give everyone else the normal button:

<!--[if mso]>
  <v:roundrect href="{{ params.cartUrl }}" style="height:70px;width:260px;" arcsize="17%" fillcolor="#0055FF">
    <center>Return to Your Cart</center>
  </v:roundrect>
<![endif]-->
<!--[if !mso]><!-->  ...the normal button...  <!--<![endif]-->

Two conditional comments make sure only one shows. In the plain HTML version I also wrote Outlook's "ghost tables" by hand around every section. I have not seen this email's button in real Outlook. It follows the pattern MJML itself writes, and I checked it in a browser, which is all I can say for this build.

Fault 4: Outlook.com's dark mode, and where the dark rules go

Dark mode is plain CSS, and where you put it decides whether light mode survives. My dark rules sit inside a prefers-color-scheme block, so light mode cannot change. Outlook.com and the Outlook applications are handled separately, because I target them with the attributes they add when they recolour an email:

@media (prefers-color-scheme: dark) {
  .dm-white, .dm-white > table, .dm-white > table > tbody > tr > td { background: #1c1c1e !important; }
  .dm-text div { color: #f2f2f2 !important; }
}
[data-ogsb] .dm-white { background-color: #1c1c1e !important; }   /* Outlook.com */
[data-ogsc] .dm-text div { color: #f2f2f2 !important; }

Gmail recolours emails by its own rules, so nothing here switches it on. As for Outlook.com, I tested these rules in a different project, one that is not published here. I did not test them in this cart build, so for this email they are written, and the light mode is proven unchanged.

Fault 5: Gmail's limits, and measuring the file that is really sent

Gmail clips an email over about 102 KB, hiding the rest behind "View entire message", and it ignores embedded CSS past about 16,384 characters. Both limits apply to the built file, not to the MJML. This is where my own checks were wrong. At one stage they reported the email at 37.1 KB, while the file the build wrote was 41,732 bytes, which is 40.8 KB. The checks were measuring MJML's unformatted output, and the build writes the formatted one. Nothing was near the limit, but a measure that disagrees with the file you hand over is not one to trust. They now measure the built file: for the finished email, 44.0 KB and 3,562 characters of style.

What the built HTML contains that the MJML never mentions

The first surprise, when I started reading what MJML builds, was how much of it is not my design at all. It is the groundwork every email needs, and if you have only ever worked in the framework, you have never had to look at it.

The resets

Near the top of the built file is a block of rules before any of my styling:

body { margin: 0; padding: 0; -webkit-text-size-adjust: 100%; -ms-text-size-adjust: 100%; }
table, td { border-collapse: collapse; mso-table-lspace: 0pt; mso-table-rspace: 0pt; }
img { border: 0; height: auto; line-height: 100%; outline: none; text-decoration: none; -ms-interpolation-mode: bicubic; }
p { display: block; margin: 13px 0; }

Each line exists because some client does something unwanted. The body rule removes the margin a client adds around the whole email, and the two text-size-adjust lines stop some mobile clients enlarging text on their own. The table rule, with its two mso lines, removes space that Outlook adds around tables. The img rule stops borders and outlines on images, makes them scale with their container, and smooths a scaled image in Outlook's engine. The p rule sets the paragraph margin explicitly, because clients disagree about the default. If you do not know the reason for a line, you cannot tell which ones are safe to remove, or which new client needs a new one.

Outlook's own settings

Just after the resets, inside a conditional comment that only Outlook reads:

<!--[if mso]><noscript><xml><o:OfficeDocumentSettings>
  <o:AllowPNG/><o:PixelsPerInch>96</o:PixelsPerInch>
</o:OfficeDocumentSettings></xml></noscript><![endif]-->

That is how an email asks Outlook for Windows to draw it at 96 pixels per inch. Without it, Outlook can scale an email up on a high-resolution screen. I wrote about that scaling problem in Where Transactional Email Fails.

The preheader

Before the visible email there is a hidden line:

<div style="display:none;font-size:1px;color:#ffffff;line-height:1px;max-height:0px;max-width:0px;opacity:0;overflow:hidden;">
  Something in your cart, still interested?
</div>

The inbox shows that text next to the subject. MJML writes it from one line, mj-preview. In plain HTML you write it yourself, and you hide it several ways at once, because different clients ignore different ones.

The small details

Counting in the finished email, these are the details I would never have chosen to write, and would miss if they were gone:

Fixed, fluid and hybrid layouts

There are three ways to make an email fit a screen, and a framework picks one for you. You need to know which, and why, before a design asks for something different.

ApproachHow it worksStrengthWeakness
FixedA table with a fixed width, such as 600pxSimple and predictableToo wide for a phone unless something shrinks it
FluidPercentage widths, and images at 100%Follows the screenLittle control on large screens, and it leans on client support for CSS
HybridFluid blocks with a maximum width, plus fixed-width tables for Outlook in conditional commentsWorks across the widest range of clientsMore markup, and you maintain the Outlook tables

The cart email is hybrid. This is the real structure MJML built for three columns, shortened:

<div style="margin:0px auto;max-width:600px;">
  <table style="width:100%;"><tr>
    <td style="direction:ltr;font-size:0px;padding:10px;text-align:center;">
      <!--[if mso | IE]><table role="presentation"><tr><td style="vertical-align:top;width:191px;"><![endif]-->
      <div class="mj-column-per-33" style="font-size:0px;display:inline-block;vertical-align:top;width:100%;"> ...column... </div>
      <!--[if mso | IE]></td><td style="vertical-align:top;width:191px;"><![endif]-->
      <div class="mj-column-per-33" style="font-size:0px;display:inline-block;vertical-align:top;width:100%;"> ...column... </div>
      ...

And the CSS that makes it respond:

@media only screen and (min-width:480px) {
  .mj-column-per-33 { width: 33% !important; max-width: 33%; }
}

Read it closely and you see how it works. Each column is an inline block, 100% wide by default, so on a phone the columns stack. The media query only widens them to a third from 480px up. That is mobile-first: if a client ignores the media query, the columns stay stacked and readable. The max-width:600px container does the fluid part. And Outlook for Windows ignores both max-width and side-by-side blocks, so the conditional comments add real tables with fixed widths just for it.

When the design changes

Designs change. A client asks for two products side by side on a phone, or the image above the text on a desktop and below it on a phone, or a banner with text laid over a picture. Some of that MJML does. Some of it it fights, and I wrote up one place it does in images shrinking and spacing apart in columns. Reversing the order in which columns stack on a phone, for example, is done with direction: rtl on the row and direction: ltr on each cell, which is HTML and CSS you write yourself. Either way, the file that is sent is HTML and CSS, so the change ends up there.

Web fonts and fallbacks

The built email links the Ubuntu web font in two ways, and fences both off from Outlook:

<!--[if !mso]><!-->
<link href="https://fonts.googleapis.com/css?family=Ubuntu:300,400,500,700" rel="stylesheet" type="text/css">
<style type="text/css"> @import url(https://fonts.googleapis.com/css?family=Ubuntu:300,400,500,700); </style>
<!--<![endif]-->

A client that blocks external fonts falls back along the font stack, Ubuntu, Helvetica, Arial, sans-serif, so the stack matters as much as the link. This also exposes a real limit in my own proof. My pixel comparison blocks web fonts for both emails, so both render in the fallback font. My hand-written version does not link the web font at all, so where that font loads, the two emails will not look identical. The test proved what it could prove. The hand-written file needs the same few lines.

When it is not my file

A framework only helps if the file you are given has one. Often it does not. I take over an email another developer built by hand, or one exported from an editor, or one edited after the build, and I am asked for an overhaul or a few adjustments. That is where the HTML and CSS stops being optional. I read it from the top:

  1. The head: the language, the viewport, the meta tags, the resets and Outlook's settings.
  2. How the width is built: fixed, fluid or hybrid.
  3. The conditional comments: what Outlook gets that nobody else does.
  4. The media queries: exactly what changes on a phone.
  5. Dark mode: any prefers-color-scheme block, the Outlook selectors, the colour-scheme tags.
  6. Where each style lives: inline, in the style block, or both, and any !important fighting another rule.
  7. Links and images: real addresses, alt text, sizes, https.
  8. The size of the finished file.

Before I change anything, I copy the file and keep the copy, run my checks to get a baseline, change one thing at a time, and compare before and after. That is the routine in the cart build: saved snapshots, checks, and a pixel comparison. I also never trust an editor's preview, because some editors rewrite markup when they save, so I read what was actually stored.

What I would learn first

If you write email and want to stop depending on a tool:

  1. The box model, and what padding, margin and width really do to a table cell.
  2. Nested tables, and why email still uses them for layout.
  3. Inline styles, and which CSS each email client reads and ignores.
  4. The resets, and the reason for every line in them.
  5. Fixed, fluid and hybrid layouts, and how columns sit side by side and stack: inline blocks, a font size of zero, and a media query.
  6. Conditional comments, and what Outlook for Windows does differently.
  7. The preheader, web fonts and their fallbacks.
  8. How to read the built HTML, and someone else's file, from the top, every time, before you trust it.

Takeaway

An abstraction layer is good. It also hides things, and some of what it hides is exactly what you need to know: the fundamentals underneath it, and the limits of the framework itself. MJML will not do everything. Designs change, a client's email arrives built by someone else, and something goes wrong in one client at the worst time. The day that happens, you need to be able to get into the HTML and CSS and fix it. So use MJML, keep reading what it builds, and know the layer underneath well enough to write the whole email without the tool, because that is the day you find out whether you understand your own email.

Frequently Asked Questions

Should I learn MJML or plain HTML first?

HTML and CSS first. MJML is a faster way to write what HTML and CSS already do, and it is an abstraction layer on top of them. If you know the layer underneath, MJML is a tool you control. If you do not, the first fault it hides from you is one you cannot find.

Is the HTML that MJML builds ready to send as it is?

Not without reading it. In the build I describe, the built HTML showed a button drawn as a paragraph, a width that made the page too wide for a phone, and a rule that became display flex on a table cell. All three were invisible in the MJML.

Why write the whole email again as plain HTML?

Some clients want plain HTML with no build step, and it proves that I understand the email without the tool. I compared the two pixel by pixel in light and dark mode. The first attempt was 60 pixels off in dark mode, because I had put a rounded corner on the wrong element.

Does MJML handle dark mode and Outlook for you?

No. Dark mode is CSS that I write, inside a prefers-color-scheme block, with separate rules for Outlook.com. The rounded Outlook button is VML that I write by hand in a raw block. I did not test the Outlook parts of this cart email in real Outlook. I have tested Outlook.com's dark-mode rules in a different project, which is not published here.

What does MJML's strict mode catch?

It refused an invalid unit and a colour with no hash when I tested version 5.4.1. It accepted a missing closing body tag, a repeated attribute and a button with no link, so I wrote extra checks for those.

What are Gmail's limits for an email?

Gmail clips an email over about 102 KB, and ignores embedded CSS past about 16,384 characters. Both apply to the built file, not to the MJML, so measure the HTML that is really sent.

What is a hybrid email layout?

A layout built from fluid blocks with a maximum width, so it follows the screen, plus fixed-width tables in conditional comments for Outlook for Windows, which ignores maximum widths and side-by-side blocks. The cart email is built this way. Its columns stack by default and sit side by side from 480 pixels up.

What do the reset lines at the top of an email do?

Each exists because some client does something unwanted: adding a margin around the body, enlarging text on a phone, adding space around tables in Outlook, or putting a border on a linked image. Learn the reason for each line before you remove one.

How do you work in an email someone else built?

I read the HTML from the top and work out the width approach, the conditional comments, the media queries and the dark mode. Then I copy the file, run my checks for a baseline, change one thing at a time, and compare before and after.
