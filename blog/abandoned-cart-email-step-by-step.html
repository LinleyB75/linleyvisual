Building an Abandoned Cart Email, Step by Step: HTML, CSS, MJML, Node.js and Brevo

Published 6 November 2026 • By Linley Bignoux • Built for: Kick Off → Your English

brevotransactional-emailabandoned-cartcase-studyhtmlcssmjmlnodejsapisystem-designdark-mode

The brief

Kick Off → Your English (Geo English) needs an abandoned cart email: the message a customer gets when they leave items in their cart. The client has agreed to be named, and its name, address and business details are used here with its permission. The email in this post is a test version. I built it for this project and made it as close to the real email as I can, so that every check here means something. The client's original source files are not published. Everything else you see is my own scripts, made-up data and screenshots.

The repository is public: kick-off-abandoned-cart-brevo. Its BUILD-LOG.md has every stage with the numbers, the raw output of every command is in logs/, and the experiments are in docs/lab-notebook.md.

My side: the design and build of the email in light and dark mode, the HTML and CSS under it, the list of values the email needs and the rules for each one, the Node.js reference for the send step and my side of the API, the email set up in Brevo, and the tests, end to end. The client's developer: connects it to their application, decides when it is sent, sends the real values, and keeps the API key.

A note on how this was recorded. Each stage is its own commit. The raw output and the pictures for the early stages were recorded afterwards, from the files I saved at the end of each stage, and the build log says so. I built an earlier email the same way: the payment failure email.

Status

Done: built, checked, and fixed until it passes. Dark and light mode. A data design with 26 deliberate breaks and 15 send tests. The same email written a second time as plain HTML, pixel-identical to the MJML build. A real send through my own Brevo account, which arrived as it should. Opened in real email clients. A one-page handoff for the client's developer.

Not tested: Outlook, in any version. The rounded Outlook button is written and checked, but I have never seen it in real Outlook, and I say so everywhere it matters.

Waiting for the client: the real links, the subject line, whether the email needs an unsubscribe link, and whether showing one product is enough.

HTML and CSS first, MJML on top

I do not only write MJML. In every project I end up in the HTML and CSS, many times: to change a spacing, to fix how one email client draws something, to read what the build produced, or to hand a developer a file with no build step. Vanilla HTML and CSS are the foundation of everything I do in email. MJML is an abstraction layer. It writes the nested tables for me, and I am glad of it, but it sits on top of HTML and CSS, and the faults that matter live underneath.

This project shows why that matters, in five places:

  • The draft was 440px wide on a 320px phone. I found out by reading the HTML that MJML had built. The button had no link, so MJML drew it as a plain paragraph, and the CSS rule meant to style it never applied.
  • The rounded Outlook button is not MJML. It is VML inside conditional comments, written by hand, and Outlook for Windows is the only client that reads it.
  • Outlook.com's dark mode is a CSS attribute selector. It marks its dark mode with data-ogsb and data-ogsc, so those rules are plain CSS.
  • Gmail's limits are about the built file: it clips an email over about 102 KB, and ignores CSS past about 16,384 characters. I measure the HTML that is actually sent, not the MJML.
  • I wrote the whole email a second time as plain HTML, with no MJML, and proved it pixel-identical to the MJML build. My first attempt was 60 pixels off in dark mode, in the rounded corners of one box. MJML puts the corner on the table, and I had put it on a cell two tables deeper. Only someone reading the built HTML would know.

Knowing the fundamentals is what lets me use MJML as a tool and not as a crutch: the box model, tables, inline styles, how email clients lay out columns, conditional comments, and the CSS that each client does and does not read.

How everything connects: the system behind the API

An abandoned cart email is not one file. It is a chain, and every link has an owner and its own way of failing. Understanding the whole system is what lets me design the email, define the data, write my side of the API, and trace a problem to the right place.

Reading it from the bottom up is how I trace a problem. If a customer sees a broken email, is it the inbox, the HTML, the way Brevo filled in the values, the request, or the data that left the shop? Each boundary has its own check, so the answer is a measurement and not a guess.

Two words get used loosely here, so I define them the way I use them. Architecture is the set of decisions that are expensive to change once other people build on them: the chain above, who owns each link, and the request with its six values. Once the client's developer has built against those, changing them costs them work. Design is everything inside my own links that I can change without anyone else noticing: the checks, the tests, the internals of the send step, and the HTML and CSS. People draw the line between the two in different places, and that is fine. What matters is knowing which decisions are the expensive ones before you make them.

The design decisions that sit at those boundaries:

  • One flat object of six values, every one of them text. A flat list is easy for the client's developer to send and easy for me to check. Even the quantity is sent as text.
  • The price arrives already formatted, with its currency, as $19.99 AUD. The application knows the currency and the format. The email must not guess either.
  • The first name is optional, and the email carries its own fallback: the heading reads "Your Cart Alex... below" with a name, and "Your Cart... below" without one. The application does not have to handle the missing case.
  • The email is found by its template ID, a stable handle that lives in the client's own Brevo account. The request is only that ID, the recipient and the six values.
  • The API key never touches the repository. It sits in the client's environment, and in mine it sits in a .env file that Git ignores and a pre-commit guard refuses to commit.
  • Limits are part of the design: one set of values must stay under 100 KB, a cart link may carry a cart id but never a password, and no value may look like a card number or a Brevo key.
  • The sandbox, the real send and the log each answer a different question. The sandbox checks the request and sends nothing. The real send shows what Brevo did to my HTML. The log, found by the message ID, shows what happened after.

Step 1: set up, and put the key guard in first

This repository is public, so a leaked API key would be public too. Before any email file went in, I made a new repository, installed a pre-commit guard, and tested it with fake keys. The guard refuses a commit that contains a .env file or anything shaped like a Brevo key.

git init -b main
npm run setup:hooks
Set-Content -Path test-key.txt -Value "BREVO_API_KEY=xkeysib-0123456789abcdef..."   (a fake key)
git add test-key.txt
git commit -m "this must be blocked"

Both attempts were blocked, and git log afterwards said the branch had no commits yet, so nothing had slipped through. The key in the picture is a made-up string with the right shape. The first real commit was the guard itself, so every later commit went through it.

Step 2: build the checks before touching the draft

I did not start by fixing the draft. I started by building the checks, so that every later stage is tested the same way.

CheckWhat it does
SyntaxThe MJML strict build, plus source checks that strict mode does not make
AccessibilityThe built email in a real browser, in light and dark mode and at 320px, with axe-core rules for email, plus language, title, alt text, link names and headings
ContrastEvery piece of text against the background it really sits on, in both modes. 4.5:1 for normal text, 3:1 for large text
PaletteContrast ratios for a set of colours, so colours are chosen by number before they are used

Why a strict build is not enough. I tested MJML 5.4.1 directly. Strict mode accepted a missing closing body tag, a repeated attribute, and a button with no link. It refused an invalid unit and a colour with no #. So the source checks cover what strict mode lets through.

npm install --save-dev mjml playwright axe-core
npx playwright install chromium
node email-checks/run.js email-checks/example/broken-email.mjml --out email-checks/example
node email-checks/palette.js "#ffffff" "#0056b3" "#007bff"

A tool you have not seen fail is a tool you cannot trust. The deliberately broken email fails with 17 errors, and the palette tool shows why a familiar link blue is a problem: #007bff on white is 3.98:1, under the 4.5:1 that normal text needs.

Step 3: the first check of the draft

The draft is 177 lines of MJML that I wrote, as close to the real email as I could make it. It mixed two brands: the title and the logo text said Frameler eyewear, while the product, price and footer were Kick Off Your English. The email is for Kick Off → Your English.

node email-checks/run.js stages/01-draft-as-received.mjml --out reports/first-run

The first run: 12 errors and 4 warnings. The strict build passed. Every error came from the checks around it. Then I read the draft myself and saw three kinds of fault the checks had missed: links like #home and your-facebook-link, a serif fallback on a sans-serif font, and icons that build share links. I added a check for each, and the count rose to 21 errors and 7 warnings. I kept the first report, so both numbers are in the repository.

Step 5: dark and light mode, and proving light did not change

The rule for this stage: light mode must not change. So I built the proof first. A comparison test renders two emails in light mode with the same grey stand-in for every image, at three widths, and counts the pixels that differ. I tried it on an email against itself, which must be identical, and on the draft against the fixed email, which must not be. Only then did I change the email.

The dark mode is plain CSS. The dark rules sit inside @media (prefers-color-scheme: dark), so light mode cannot change:

@media (prefers-color-scheme: dark) {
  body, .dm-page { background-color: #121212 !important; }
  .dm-white, .dm-white > table, .dm-white > table > tbody > tr > td { background: #1c1c1e !important; }
  .dm-text div { color: #f2f2f2 !important; }
}
[data-ogsb] .dm-white { background-color: #1c1c1e !important; }   /* Outlook.com */

Outlook for Windows gets the rounded button as VML, and every other client gets the normal one. Two conditional comments make sure only one shows:

<!--[if mso]>
  <v:roundrect href="{{ params.cartUrl }}" style="height:70px;width:260px;" arcsize="17%" fillcolor="#0055FF">
    <center>Return to Your Cart</center>
  </v:roundrect>
<![endif]-->
<!--[if !mso]><!-->  ...the normal button...  <!--<![endif]-->

Step 6: define the data the email needs

Six things in the email were typed in: the customer's name, the product, its picture, the price, the quantity and the cart link. A real cart email needs each of them to come from the application. Working out exactly what it must send, and refusing anything wrong before it is sent, is my side of the API.

ValueRequiredThe rule
firstNameOptionalText, up to 40 characters. Without it the heading reads "Your Cart... below"
productNameRequiredText, up to 120 characters. Also the product picture's alt text
productImageUrlRequiredAn https address, no spaces, no username or credential in it
priceRequiredText with a number in it, sent exactly as it should be shown
quantityRequiredA whole number from 1 to 999, sent as text
cartUrlRequiredAn https address, no spaces. A cart id is fine, a password or secret is not
 
{
  "to": [{ "email": "customer@example.test", "name": "Alex" }],
  "templateId": 12,
  "params": {
    "firstName": "Alex",
    "productName": "Kick Off Your English Ebook CAT01",
    "productImageUrl": "https://res.cloudinary.com/.../product.png",
    "price": "$19.99 AUD",
    "quantity": "1",
    "cartUrl": "https://shop.example.test/cart/restore?cart=TEST-0001"
  }
}

This is the whole agreement between my side and the client's developer, written as data. The values are made up. A generated page, docs/data-design.md, holds the same table for them.

A gap in my own pipeline. My first version could check that a value was present, short enough and safe. It could not check that a quantity was a number, so a quantity of "one" or a price of "free" would have passed. I added a format rule, and a deliberate break for each format. The tests then had 26 cases: every required value missing, a misspelt name, http instead of https, a space in an address, a credential in an address, a quantity that is not a number, a price with no number, HTML, Brevo tags, a number instead of text, a value too long, a card number, a Brevo key, and a request over 100 KB. All 26 are caught.

Then my own checks had a blind spot. The email now had tags in it, and the checks passed it with the tags as plain text:

The checks passed, but they had measured the words {{ params.productName }}, not a product. A long product name would never have been tried. So I taught the checks to fill the email in with test data first, the way Brevo will, and then compare. With the old typed-in values filled in, the new email was identical to the previous stage in light and dark, at all three widths. With a different customer filled in, a few thousand pixels differed, so the test can tell.

I tested the send step against a small simulated Brevo that I wrote, and it has 15 tests: the dry run, the sandbox, typing SEND to confirm, a wrong key, a missing key, and refusing bad data before any request. The whole walkthrough passes with 9 checks and 1 warning, and the warning is honest: the social and footer links still point at example.com.

Step 8: the same email as plain HTML, with no MJML

Some clients want plain HTML and no build step, and some developers will edit the final HTML. So I wrote the whole email a second time by hand, as nested tables with inline styles: the same six tags, the same dark rules, the Outlook button and its ghost tables. It is indented so a person can read it, with a comment above each section.

  • The same checks pass: 0 errors, 1 warning (the placeholder links), the same lowest contrast of 5.05:1.
  • The same six tags, with the same counts.
  • The same pixels: compared with the MJML build, with the same data filled into both, 0 pixels differ, in light and dark, at 600, 414 and 320px.
  • The test can say no: one text colour wrong by a single level out of 255 shows hundreds of differing pixels, and one extra pixel of padding changes the page height.

My first attempt was identical in light mode and 60 pixels off in dark mode, all in the rounded corners of the white box in the orange band. This is the difference. MJML puts the corner on the table itself, and the text cell sits directly inside it:

<table style="background-color:#FFF;border-radius:8px;border-collapse:separate;" width="100%">
  <tr><td class="dm-text" style="padding:10px 25px;"> ...the heading... </td></tr>
</table>

I had put the corner on a cell nested two tables deep, so the dark background showed through differently at the corners. Moving it to the table made the two emails exactly equal. It is a good example of why I read the HTML that MJML writes.

Step 9: real Brevo

Everything so far used my simulated Brevo. The simulation follows Brevo's documented behaviour, but it is not Brevo, so this step uses the real one, in the same order every time: look, check, send.

  1. I made an API key in Brevo with a short expiry, and put it only in .env. I never paste the key into a chat, a screenshot or a file that is committed.
  2. I made the email in Brevo from the built dist/email.html: a new transactional email, my own HTML pasted in, then Save and Activate. I copied its template ID into .env with my own test address.
  3. npm run send:dry prints the request and sends nothing. I check the masked address, the template ID and the six values.
  4. npm run send:sandbox sends the request with Brevo's sandbox flag. Brevo's documentation says it only checks the request, sends nothing and leaves no log, so it cannot show how the email looks.
  5. npm run test:brevo runs the whole walkthrough and sends exactly one real email to my own address, only after I type SEND.

The email arrived in my inbox, and everything in it was as it should be. Brevo's documentation also warns that its IP security can reject a request from an address it does not know once its learning phase ends, and that adding the address under Security, then Authorized IPs, fixes it. I did not hit it, but it is on the list for the client's developer.

Step 10: real email clients

I sent the real email to my own addresses and opened it in real email clients, in light and in dark mode. What each one did, with pictures, is recorded in the repository, in evidence/stage-7-clients/RESULTS.md. Gmail recolours emails by its own rules, so a client's own dark mode can change what I designed, and that is exactly what this step is for.

Not tested: Outlook, in any version. I stopped here on purpose. The Outlook button and the Outlook dark-mode rules are written and checked in a real browser, but they have never been seen in real Outlook, and the build log and the handoff both say so.

Step 11: write it up, and hand it over

A recorder script runs the checks for a stage, saves the raw output with the time and the exit code, and takes pictures of the email in light and dark mode. The build log has every stage with its numbers, the lab notebook has the experiments behind each decision, and a one-page handoff tells the client's developer what they receive, how to set the email up in Brevo, what their application sends, and what is still open. The last command is the setup check:

npm run verify
All checks passed. Ready to push.

What went wrong

  1. My first run of the checks missed three kinds of fault. I found them by reading the file and added checks.
  2. The first fix for the button looked right and was not. Measuring showed the clickable area was smaller than the visible button.
  3. I wrongly believed strict mode catches a missing closing tag. Testing showed it does not, which is why the source checks exist.
  4. The checks measured a different size from the file I would hand over. They measured 37.1 KB of unformatted HTML, and the build wrote 40.8 KB of formatted HTML. They now measure the same file.
  5. My pipeline could not check a format. It could say a quantity was present and short, but not that it was a number.
  6. My checks passed an email whose tags were not filled in. They had measured the words of the tags, not a product.
  7. The finished email was cut short on disk. After a long paste, the file stopped partway through the button block. The build came out at 23 KB instead of 45 KB, the build check said the cart link had been lost, and the pixel comparison with the plain HTML failed. I restored the file and the comparison passed. Lesson: after pasting a long file, check its fingerprint and its line count, and keep the checks that noticed.
  8. I assumed the page heights would be the same on every computer. They are not. The fonts installed change how text wraps. What the test judges is whether two emails match each other on the same computer.
  9. My first plain HTML version was 60 pixels off in dark mode. The rounded corner was on the wrong element.

Takeaway

An email that depends on an API is a chain: the shop, the data, the request, Brevo, the HTML and the inbox. Each link needs its own check, and each check needs to be seen failing before you trust it. Know the system end to end so that you can trace a fault to the right link. Know HTML and CSS at the level of the tables and the styles, because MJML is an abstraction layer, and the day something looks wrong in one client, the answer is in what it writes. Keep a build log as you go, and write the mistakes in it too, because they are the most useful part.

Frequently Asked Questions

Do you write emails in MJML or in plain HTML?

Both. MJML is how I write most emails, because it is shorter and stricter. But it is an abstraction layer on top of HTML and CSS, and in every project I go into the HTML and CSS to change something, fix one email client or read what the build produced. For this email I also wrote a second version by hand as plain HTML, and proved it pixel-identical to the MJML build.

Why prove the plain HTML matches the MJML build pixel by pixel?

Because two emails that look similar are not the same email. The comparison renders both in a real browser, in light and dark mode at three widths, with the same data filled in, and counts the pixels that differ. It reported 0, and it still caught a text colour that was wrong by one level out of 255.

What tools do you need to build an email like this?

A text editor such as VS Code, Node.js 20 or newer (I used 24), Git to save and back up the project, MJML to write the email, and a Brevo account to set it up and send it. The checks use Playwright, which drives a real browser, and axe-core for accessibility rules.

What does the application have to send to Brevo?

One request with the recipient, the ID of the email in Brevo, and six values: the first name (optional), the product name, the product picture's address, the price already formatted, the quantity and the cart link. Every value is text. I define the values and the rules for each, and the client's developer sends them.

Can you test a Brevo email without sending it?

Partly. The sandbox flag checks the request without sending or logging anything, and a simulated Brevo covers the sequence of steps. Neither shows how the email looks, so I also sent a real email to my own inbox and opened it in real email clients.

Who connects the email to the shop?

The client's developer. I design, develop and test the email end to end, define what data the application sends, and write my side of the API call. They decide when it is sent, send the real values, keep the API key and make the production call to Brevo.

Did you test it in Outlook?

No. I tested it in a real browser and opened it in other real email clients, but not in Outlook, in any version. The rounded Outlook button and the Outlook dark-mode rules are written and checked, but I have never seen them in real Outlook, and the repository says so.
