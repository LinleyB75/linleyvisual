Brevo 2FA Setup Email: A Development Pipeline from MJML to Tested Send

Published 28 October 2026 • By Linley Bignoux • Built for: Kick Off → Your English

brevotransactional-emailcase-studydevelopment-pipelinemjmltesting2fa

The pipeline in one view

This case study follows one email, a two-factor setup notification for Kick Off → Your English (Geo English), through the development pipeline I use for transactional email: from a supplied MJML file to a tested send in Brevo. The client agreed to be named, and every value in this post is made-up sample data.

The pipeline is eight stages in a fixed order, each with its own check. A mistake fails early and cheaply, and nothing reaches a real inbox until the later stages.

What runs it: Node.js

The whole pipeline runs on Node.js, with three packages: MJML for the build, dotenv to read the settings file, and nunjucks for the simulated Brevo only. The calls to Brevo use Node's built-in fetch with a 10 second timeout, the SEND prompt uses readline, and the simulated Brevo uses the built-in http module.

So the pipeline needs Node.js 20 or newer, and I would use 22 or 24. The Node.js release schedule says production applications should only use an Active or Maintenance LTS release. I haven't tested Node 26. Check yours first with node --version.

Stage 2: Fix the source

The social icons. The standard MJML icons are always white. To get orange icons on the client's grey, I drew four custom ones (Facebook, X, Instagram, YouTube) as small transparent PNGs in the client's orange, #EA6D2F, from Font Awesome Free brand shapes (licensed CC BY 4.0). They sit on the grey, #DFE0E5, with no box behind them.

The newsletter line. A security email should do one job. A newsletter invitation competes with the button, and promotional content can blur whether a message counts as transactional. That is not legal advice, so check with the client if it matters.

The footer. It is laid out like the client's payment receipt: the small Kick Off logo, "brought to you by Geo English", the round Geo English logo and the address. On phones the logo and its text centre when the columns stack.

What I leave alone. The black header and the body colours. I compared the header with the original in a real browser at 700 px wide, and it is identical pixel for pixel.

Stage 3: Define the data

Three fields. The project uses example names, and the client's developer maps their own names onto them.

Example nameRequiredExample (made-up)If missing
firstNameNoAlexThe greeting becomes "Hi there,"
maskedUsernameYesa******eThe username line would be empty
setupUrlYeshttps://app.example.com/2fa/setup?token=SAMPLE-TOKEN-123The button has no link

I define the field list and what each value must look like. The client's system produces the values.

This stage also decides what the email must never contain. A two-factor setup email is a notification, not a way to deliver secrets. It never carries a verification code, a backup code, a setup key or a QR link, because anyone who can read the email could use them. That is my recommendation, not a Brevo rule. It shows the username only in masked form, and the button should lead to a link that the client's system creates, uses once and expires. That is what I ask the client's developer to provide. I don't see or test their system.

Stage 4: Build

The build compiles the MJML in strict mode, so a mistake stops it with the line number. A short script then warns about leftovers that must be fixed before the email goes into Brevo: placeholder icon links, links still pointing at example.com, social links that go to the sites' home pages, and a size near Gmail's clipping limit. The built email is about 35 KB.

A fresh copy of the project failed to build at first. Git doesn't keep empty folders, so there was no folder for the built email. It only showed up when I unpacked the project into a clean folder and ran everything from scratch. A small step now creates the folder.

Stage 5: Check the data

A script reads the email to work out which fields it uses (the ones inside an {% if %} are optional), then checks the sample data. It refuses anything that must never be in a two-factor email:

  • a QR or authenticator link (otpauth://)
  • a 6 to 8 digit number that could be a verification code
  • a long string shaped like a setup key
  • a full phone number, or an email address that isn't masked
  • HTML, or template tags, so a value can't change the email
  • a link that doesn't start with https://
  • a params object over the 100 KB that Brevo's documentation allows

There are 17 test cases: 3 that must pass and 14 deliberate breaks, such as a code in the first name, a setup key, a QR link, a phone number and a misspelt field name. All 17 behave as expected.

These rules guess at the shape of a code or a key, so they can flag something harmless. I would rather get too many flags than miss a real one. They check the sample data, not what the client's system really sends, so the handoff includes the same check for their developer to run on a real request.

Masking, card data and PCI DSS

Mask at the source, check at the edge. I ask the client's system to mask personal values before they reach the email, so the username should arrive as a******e and never in full. My data check refuses anything that isn't masked: an email address, a full phone number, or a username without a *. The send script masks the test address in everything it prints, as t***@example.com, and never prints the API key.

What PCI DSS covers. PCI DSS is the payment card industry's data security standard, and it is about card data. This two-factor email carries none, so it isn't a PCI DSS question. PCI DSS has its own two-factor rule (requirement 8.4), but that decides who must use multi-factor authentication to reach card systems, which is a different question from this notification. The same pipeline also builds receipt emails, where card data does matter. In version 4.0.1, requirement 3.4.1 says a card number is masked when displayed, with no more than the first six and last four digits ever shown (the same rule was numbered 3.3 in version 3.2.1), and the standard says unprotected card numbers must not go out through end-user messaging such as email.

In my receipt build, the data check is stricter than the rule. It accepts only the last two to four digits of a card, and it refuses any run of 13 to 19 digits anywhere in the data, so a full card number can't slip into a field by mistake.

I'm not a PCI assessor, and whether a system is in scope is for the client's acquirer or assessor to decide, so confirm it with them. Also check what your Brevo plan keeps in its logs, and for how long, rather than assuming.

Stage 6: Send, safely

CommandWhat happens
npm run send:dryPrints the request and sends nothing. This is the default
npm run send:sandboxCalls Brevo with its sandbox flag: nothing is sent and no log is made
npm run send:liveSends one email to my own test address, after I type SEND

The data must pass the stage 5 checks first. The API key is never printed, the test address is masked, there is only ever one recipient, and the script says plainly that accepted is not the same as delivered.

The sandbox flag goes in the JSON body, in a headers object, not in an HTTP header:

{
  "to": [ { "email": "you@example.com", "name": "Alex" } ],
  "templateId": 12,
  "params": { "firstName": "Alex", "maskedUsername": "a******e", "setupUrl": "https://app.example.com/2fa/setup?token=SAMPLE-TOKEN-123" },
  "headers": { "X-Sib-Sandbox": "drop" }
}

Brevo's documentation says the sandbox sends no email and makes no log, and that it only checks the format of the request. A Brevo community answer reports that putting the flag in a real HTTP header still sends live emails, which is why the script uses the body.

Stage 7: Test in layers

The cheapest checks come first. Before touching a real account I test the whole sequence against a simulated Brevo on my own computer. It follows what Brevo's documentation says: requests carry an api-key header; a template must exist and be activated; the template's sender and subject apply unless the request overrides them; the sandbox flag means no email and no log; one params object can be up to 100 KB; and the log needs an email, a template ID or a message ID.

It does not show how real Brevo treats the HTML, special characters or its editor, and its error messages aren't Brevo's. The honest label for these results is simulated testing. What the walkthrough showed:

  • Sending before the template was activated was refused, with a "not found or not activated" message.
  • After activation, the sandbox call was accepted and left no log entry.
  • A wrong API key was refused with a 401.
  • A live send returned a message ID and one log entry.
  • The saved message passed five inbox checks and gave two warnings: the icon links were still placeholders, and the policy link still pointed at example.com. Both warnings were correct, because those two items were still placeholders at that point.
  • With the first name removed, the greeting fell back to "Hi there,".

The same walkthrough then runs against a real Brevo account with one command, npm run test:brevo, and the email is checked in real email clients. The simulated stage and the real stages use identical steps, so a fault found early is cheap to fix and a fault found late is rare.

Stage 8: Hand over

The client's developer gets what they need to connect it: the field table, a sample request, and the same data check to run on a real request. A build log records every stage, and a setup checker confirms that every file is the latest version, that nothing from an earlier version is left over, and that nothing which must not be pushed, such as an API key, is in the project. The developer maps their own field names onto the three example names, connects the email to their system, and sends it.

Four bugs the pipeline caught

  1. Typing SEND counted as cancelled. The prompt's close handler ran before the answer was recorded. The send tests caught it.
  2. The test harness blocked its own simulated server, so requests timed out. It was fixed by starting the script asynchronously.
  3. A fresh copy of the project couldn't build. The clean-folder run caught it.
  4. The build needs Node.js 20 or newer. It passed on one version and only failed when I ran the whole project on five.

All four were invisible until something ran them. I haven't verified this email in every email client, so test it in yours before relying on it.

Takeaway

A transactional email is a chain, and a development pipeline gives every link its own check. Here the data is the risky part, so it got three fields, a list of things that must never appear, and tests that prove the checks fire. Put the cheap, loud checks first, send nothing real until the end, and run the whole project from a clean copy, on more than one Node.js version, before you trust it.

Frequently Asked Questions

What is a development pipeline for a transactional email?

A fixed order of stages, each with its own check, so mistakes fail early and cheaply. For this email: compile the supplied file in strict mode, fix the source, define the data, build, check the data, send in safe modes, test in layers and hand over. Nothing reaches a real inbox until the later stages.

Should a two-factor setup email contain the verification code?

In this build, no. It is a notification that two-factor authentication has been switched on, with a button to finish setting it up. It never carries a verification code, a backup code, a setup key or a QR link, because anyone who can read the email could use them. That is my recommendation, not a Brevo rule.

Can you test a Brevo transactional email without sending it?

Partly. Brevo's sandbox accepts a request without sending an email and without making a log, but it only checks the format of the request, not how the email looks. A dry run and a simulated Brevo cover more of the sequence, but a real send to your own inbox and a check in real email clients are still needed.

Which version of Node.js does this pipeline need?

Node.js 20 or newer. I ran the whole project from a clean copy on Node 16, 18, 20, 22 and 24. The build fails on 16 and 18, and everything passes on 20, 22 and 24. Node 18 reached end of life in April 2025 and Node 20 in April 2026, so use 22 or 24. I haven't tested Node 26.

Does PCI DSS apply to a two-factor setup email?

Not to this email, because it carries no payment card data. PCI DSS has its own two-factor rule, but it governs who may reach card systems, not a notification like this. It does matter for emails that show a card, such as receipts: PCI DSS v4.0.1 requires a card number to be masked when displayed, with no more than the first six and last four digits shown, and says unprotected card numbers must not be sent by email. I am not a PCI assessor, so confirm the scope with the client's acquirer or assessor.

No. I work out what data your application needs to send, build and test the email, and set it up in your email platform. Your developer connects it and sends it. I can supply a sample request and a Node.js reference implementation of the send step for them to adapt.
