Building a Payment Failure Email, Step by Step: MJML, HTML, CSS, Node.js and Brevo

Published 3 November 2026 • By Linley Bignoux • Built for: Kick Off → Your English

brevotransactional-emailcase-studymjmlhtmlcssnodejsvs-codedark-mode

The brief

Kick Off → Your English (Geo English) sent me the MJML source of a payment failure email. It is the message a customer gets when a monthly payment could not be processed. The client has agreed to be named. The email's wording and design belong to the client. This post shows screenshots of the finished email and describes what I did to the file, but it does not publish the source files. Everything else shown is my own scripts or made-up sample data.

The brief for this round: keep the design and layout exactly as supplied, fix the syntax and the wording, use placeholder links for now, add no data values yet, and add dark and light mode.

My side: the dark and light mode design, the MJML, the Node.js scripts and my side of the API call, the Brevo email and its ID, and the tests, end to end. The client's developer: when the email is sent, the real links, the API key and the production call to Brevo.

Status

Done: built, the strict build passes, the Node.js checks and tests pass, a real Brevo email created, activated and sent to my own inbox, tested in 130 email clients, and committed and pushed to GitHub.

Waiting for the client: the real links, the subject line, and the handoff to their developer.

How MJML, HTML, CSS and Node.js fit together

Four languages work on one email, and each has its own job. I write MJML. MJML builds the HTML and CSS that email apps receive. Node.js runs the build, and the scripts that check and send the email.

LanguageWhat it does hereWhere I touch it
MJMLThe language I write the email in. It is short, and stricter than HTML.The MJML file in the templates folder
HTMLWhat the build produces: nested tables that email apps understand.dist/email.html. I read it, and I never edit it.
CSSInline styles that MJML writes, plus the head styles for dark mode and Outlook.The styles in the MJML head
Node.jsRuns the build, the checks, the tests, the send script and a simulated Brevo.The scripts in the scripts folder

The project folder

I start every email from the same starter project, so the checks and the send script are the same each time. Three files are different for each email: the MJML, the settings file, and the sample data. This is the finished folder:

Two things never go into the repository: node_modules (the installed packages) and .env (the real settings, including the API key). The supplied original file is kept out as well, because its preview text named another client.

Step 1: set up VS Code, Node.js and Git

I open the project folder in VS Code (File, Open Folder), open the terminal (Terminal, New Terminal), and check that the terminal path ends with the project folder. Then I check the tools before anything else.

The first check failed: Node.js was not installed.

After installing Node 24 LTS: v24.22.2. The 25 changes on the Source Control icon show the project was still inside my public Email-Dev repository.

node -v
git init
npm install
npm run setup:hooks

Three things went wrong on the way, and each is worth knowing about:

  • Node.js was not installed. The first command said node was not recognised. I installed Node 24 LTS, which is the version I tested this project on (node -v shows v24.22.2). I haven't tested Node 26.
  • The project was first opened inside my public Email-Dev repository. VS Code showed 25 changes. I moved the folder out before running git init, so client files could never be committed to a public repository by mistake.
  • Windows blocked npm with "running scripts is disabled on this system". One line allows it for my own user account only: Set-ExecutionPolicy -Scope CurrentUser RemoteSigned.

git init in the project's own folder, then Windows blocking npm. The error is in red.

npm install added 253 packages. It also printed a notice about a deprecated part inside MJML and 33 moderate vulnerabilities. Those are reports about the build tools on my computer, not about the finished email, which is plain HTML. I did not run npm audit fix --force, because it can change MJML's version and break the build.

npm install finishing: 253 packages added, and the notices I did not act on.

The last command installs a guard that runs before every commit. It stops a commit that contains an API key or a settings file:

# the check inside the guard
if git diff --cached -U0 | grep -E -q 'xkeysib-[A-Za-z0-9]{32,}|xsmtpsib-[A-Za-z0-9]{32,}'; then
  echo "BLOCKED: something shaped like a Brevo key is in the staged changes."
  exit 1
fi

Step 2: intake, read before changing anything

I saved the supplied MJML as templates/original.mjml, which Git ignores, and ran an intake script on it before touching anything. It builds the file twice, once softly and once in strict mode, then reports on links, images, colours and wording. It changes nothing. It found 26 points, and reading the file myself added more.

npm run intake templates/original.mjml

The most useful result: the soft build said OK, but the strict build refused the file, on an invalid attribute, an invalid unit and colours missing their hash. A closing tag was also missing near the end of the file, and neither build noticed. The intake script did not count unclosed tags at the time, so I found it by reading.

Step 3: fix the MJML

The design and layout stay exactly as supplied. I fix the syntax and the wording, and I check the result against the original in a browser, side by side, at desktop width. Four of the fixes, as small before and after pairs:

<!-- spacing: one break each, not a second break from the stray closing tag -->
before: Your payment<br></br><br></br>
after:  Your payment<br /><br />

<!-- icons: the plain link version, not a share link -->
before: <mj-social-element name="facebook" href="https://example.com/facebook">
after:  <mj-social-element name="facebook-noshare" href="https://example.com/facebook">

<!-- an invalid unit -->
before: icon-size="38rpx"
after:  icon-size="38px"

<!-- a colour that was written as a word -->
before: style="color: #BLUE;"
after:  style="color: #0000ff;"

Two of these taught me something:

  • The unit. 38rpx is not a CSS unit, so my first guess was 20 px. It was wrong. The compiled original shows the icons at 38 px. I found it by comparing the compiled output of both versions, not by guessing.
  • The colour. The word BLUE meant blue. My first replacement, #007bff, would have failed contrast on the light-blue box at 2.60:1. Real blue, #0000ff, gives 5.62:1. Measuring before choosing caught it.

Step 4: define the data

This is the step where I define what data the client's application sends. For this email the answer, by decision, is none yet. The amount, the plan name and the retry wording are fixed text, and every link is a placeholder. So the sample data file is empty, and the settings file has no data rules:

// data/params.json
{}

// project.config.js (the part about the data)
module.exports = {
  name: "Kick Off payment notification failure",
  mjml: "templates/email.mjml",
  html: "dist/email.html",
  subject: "We could not process your payment",   // the client confirms the real subject
  maxLength: { default: 200 },
  links: [],
  masked: [],
  never: [],
};

I still wrote down the list of values the email could take, so the client can decide. Names match the ones I used in the receipt email, and every example is made up:

If the client adds values, the MJML reads each one with a Brevo tag such as {{ params.total }}, the optional ones sit inside an {% if %}, and the same scripts check them: links must start with https, personal values must be masked, and nothing that looks like a card number can get through.

Step 5: dark and light mode

The email declares that it supports both colour schemes. The dark rules sit inside a prefers-color-scheme: dark block, so light mode cannot change. Outlook.com and the Outlook apps mark their dark mode with data-ogsb and data-ogsc attributes, so they get their own rules:

<meta name="color-scheme" content="light dark" />
<meta name="supported-color-schemes" content="light dark" />

/* Apple Mail, iOS Mail and other apps that follow the device setting */
@media (prefers-color-scheme: dark) {
  .dm-white { background-color: #1c1c1e !important; }
  .dm-copy div { color: #e6e6e6 !important; }
  .dm-copy a { color: #8cc4ff !important; }
}

/* Outlook.com and the Outlook apps */
[data-ogsb] .dm-white { background-color: #1c1c1e !important; }
[data-ogsc] .dm-copy div { color: #e6e6e6 !important; }

To prove the dark rules cannot touch light mode, I took screenshots with and without them: 0 pixels differ. In dark mode the page is #121212, the content areas #1c1c1e, the light-blue box #1f3a4a, and the text and links are light. The black header, the black footer and the orange button stay the same. The supplied design had no dark version, so the dark palette is my own design.

Step 6: the strict build, and reading the HTML and CSS

One command builds the email. A small script runs before it to make the output folder, and another runs after it to warn about anything that must be fixed before the email goes into Brevo:

"prebuild":  "node scripts/make-dist.js",
"build":     "mjml templates/email.mjml --config.validationLevel=strict -o dist/email.html",
"postbuild": "node scripts/check-build.js"

Strict mode refuses to build when it finds an invalid value or an attribute that does not exist, and it names the line. This is what a good build prints. The one warning is expected, because the brief asked for placeholder links:

Built dist/email.html (33 KB).

Before this goes into Brevo:
  - A link still points at example.com. Put in the real address.

The guard installed, then a good build with the one expected warning.

I then open dist/email.html and read it. This is the HTML and CSS that email apps actually receive: nested tables, inline styles, and Outlook-specific markup that MJML writes for me. I never edit this file by hand. It is rebuilt every time, so any change would be lost. If something is wrong, I fix the MJML and build again.

VS Code underlines about nine things in the built file, because its checker does not understand the Outlook markup. That is expected, and I leave them alone.

Step 7: the Node.js checks

The scripts around the email are plain Node.js, with a few packages: MJML for the build, dotenv to read the settings file, and nunjucks for the simulated Brevo only. The calls to Brevo use Node's built-in fetch with a 10 second timeout. Each script has one job:

This email has no data values yet, so the data check reports none required and none optional, and the test runs 1 case (1 of 1). When values are added, the same scripts check their names, links, masking and length.

The data check, and the first test.

The send script is my side of the API call, and it has three modes. Dry run is the default and sends nothing. The sandbox mode calls Brevo with its sandbox flag, which goes in the JSON body, not in an HTTP header. Live mode needs the word SEND typed, and goes to one address:

// Brevo's sandbox flag goes in the JSON body's "headers" object, not in the HTTP headers
if (mode === "sandbox") body.headers = { "X-Sib-Sandbox": "drop" };

Brevo's documentation says the sandbox sends no email and makes no log, and that it only checks the format of the request.

npm run test:send runs the send script against a small simulated Brevo server on my computer. It runs 14 tests: the dry run sends nothing and masks the address, the sandbox flag is in the right place, typing anything but SEND cancels, a wrong key gives a clear 401 message, a missing key or a bad template ID stops before any request, and the API key is never printed. All 14 pass.

The data test and the 14 send tests, all passing.

Step 8: a simulated Brevo

Before touching a real account, I run the whole send sequence against a simulated Brevo on my own computer. It follows what Brevo's documentation says. What the walkthrough showed:

  • A Brevo email is created inactive. Sending before it was activated was refused with a "not found or not activated" message. That refusal is on purpose, to show the mistake.
  • After activation, the sandbox call was accepted and left no log entry.
  • A wrong API key was refused with a 401.
  • A live send returned a message ID and one log entry.
  • The saved message passed six inbox checks and gave one warning, for the placeholder links. That warning is correct.

The simulated walkthrough finishing, with six checks passing and the one expected warning.

It does not show how real Brevo treats the HTML, special characters or its editor, and its error messages are not Brevo's. The honest label for these results is simulated testing.

Step 9: save it, verify and the first commit

Before the first commit I run a pre-push check. It looks at five things: the files that should exist, stray files, Git and the guard, anything shaped like a Brevo key, and that dist/email.html is newer than the MJML. It must end with "All checks passed. Ready to push."

npm run verify
git add -A
git status
git commit -m "Build the payment notification failure email for Brevo"

npm run verify passing, then git add. The line-ending warnings are harmless.

On Windows, git add prints a long list of warnings that line endings will change from LF to CRLF. They change nothing in the files, and I ignore them. Then git status shows exactly what is about to be saved. I check three things in that list: no .env, no node_modules and no simulated-inbox.

git status: the 22 files about to be committed.

The commit guard runs silently first, and speaks up only if it finds a key or a settings file. The first commit saved 22 files.

Step 10: real Brevo

Now the real account. Brevo only sends from a verified sender, so I check I have one first. Then I create the Brevo email from the built HTML. I use the option to paste my own HTML, not the drag-and-drop editor, so Brevo does not rebuild the design.

  1. In Brevo: Transactional, then Templates, then New Template. I enter a name, the subject line and the sender.
  2. I copy the whole of dist/email.html and paste it in, then Save and Activate. It cannot be sent until it is activated.
  3. The ID is the number after the # in its name.
  4. I make an API key for this project, in the API keys tab. An API key starts with xkeysib-. An SMTP key is the wrong kind.
  5. The settings go in a file called .env, which Git ignores, and the commit guard blocks as well. I never paste a key anywhere else.
BREVO_API_KEY=your-brevo-api-key-here
BREVO_TEMPLATE_ID=12
TEST_TO_EMAIL=you@example.com

After saving the file, I run git status again. It must say the working tree is clean, with no .env listed. Then the same three safe steps as before, this time against the real account:

  • npm run send:dry printed the request with my template ID and a masked address, and never the key.
  • npm run send:sandbox was accepted by Brevo, with nothing sent and nothing logged.
  • npm run send:live sent one real email to my own inbox, after I typed SEND.

I then checked the result in three places: Brevo's transactional log, my inbox, and my phone. Accepted is not the same as delivered, so I always look.

Step 11: real email clients

A browser cannot show how email apps treat an email. I tested the email in 130 email clients, before and after the dark mode and button fixes. The coverage included Outlook, webmail, mobile and tablet viewports and displays, and operating systems, with Gmail dark mode, Outlook dark mode and the Outlook 365 variants.

As usual with Gmail and Outlook, there were a number of dark mode rendering issues. The button also needed VML fixes before testing. Classic Outlook draws buttons with Word's engine, which ignores rounded corners, so a VML version of the button is used for it. After the fixes, everything rendered correctly.

I haven't listed all 130 here, so test your own audience's clients before relying on any of this.

What went wrong

  1. A closing tag was missing, and neither build reported it. I found it by reading. The intake script now counts unclosed tags and also catches buttons with no link, placeholder social links, empty links, invalid colours and broken CSS.
  2. A colour that looked invalid was a request for blue. My first replacement would have failed contrast at 2.60:1. Measuring caught it.
  3. I misread an invalid unit. I guessed 20 px, and the compiled original showed 38 px.
  4. I miscounted the send tests. I wrote 15 in my build log, and the project runs 14, because the 15th test only applies to emails with link values. Counting the real output found it.
  5. Node.js was not installed on my computer. Installing Node 24 LTS fixed it.
  6. The project was first opened inside a public repository. I moved it out before the first git init.
  7. Windows blocked npm. One line fixed it for my own account.

Takeaway

An email is a chain, and every link needs its own check. Read the file before you change it, build in strict mode, measure instead of guessing, send nothing real until the later steps, and test in real email clients. Keep a build log as you go, and write the mistakes in it too, because they are the most useful part.

Frequently Asked Questions

What tools do you need to build a transactional email like this?

A text editor such as VS Code, Node.js 20 or newer (I used 24), MJML to write the email, Git to save and back up the project, and a Brevo account to set it up and send it. The checks and the send script run on Node.js.

Why write the email in MJML and not plain HTML?

MJML is shorter and stricter, and it builds the nested HTML tables that email apps need. In strict mode the build stops on a mistake that a soft build would let through. I still read the built HTML, because that is what email apps receive.

How does dark mode work in this email?

The email declares both colour schemes, and its dark rules sit inside a prefers-color-scheme: dark block, so the light version cannot change. Separate rules cover Outlook.com and the Outlook apps, which mark their dark mode with attributes. Gmail and Outlook still gave a number of dark mode rendering issues, and the button needed VML fixes, so I tested in 130 email clients.

Can you test a Brevo email without sending it?

Partly. The sandbox flag checks the request without sending or logging anything, and a simulated Brevo covers the sequence of steps. Neither shows how the email looks, so I also sent real emails to my own inbox and tested in real email clients.

Does this email need data from the client's application?

Not yet. In this version the amount, the plan name and the retry wording are fixed text, and the links are placeholders until the client sends the real ones. If values are added later, I define the list of names and the rules first, and the client's developer sends them.

Who connects the email to the client's system?

The client's developer. I design, develop and test the email end to end, define what data the application sends, and program my side of the API call. They decide when it is sent, supply the real links, keep the API key and make the production call to Brevo.
